# Triage

让项目 issue tracker 上的 issue 流经一个由 triage 角色组成的小型状态机。

如果本仓库把外部 pull request 当作一种请求入口（见 issue-tracker 配置），triage 也覆盖它们：**PR 就是附带了代码的 issue**——相同的角色、相同的状态、相同的机器，只是下面有几处标注了 "for a PR" 的差异。按照 tracker 配置，把光秃秃的 `#42` 解析为一个 issue 或一个 PR。

triage 期间发布到 issue tracker 的每一条评论或 issue 都**必须**以这段免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何撰写经久耐用的 agent brief
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库如何运作

## 角色

两个 **category** 角色：

- `bug` — 有东西坏了
- `enhancement` — 新功能或改进

五个 **state** 角色：

- `needs-triage` — 需要 maintainer 评估
- `needs-info` — 等待报告者提供更多信息
- `ready-for-agent` — 已完整定义，可供一个 AFK agent 上手
- `ready-for-human` — 需要人类来实现
- `wontfix` — 不会处理

对于 PR，相同的状态要对照附带的代码来解读：`ready-for-agent` 表示已附上一份 brief、应由 agent 对这个 diff 采取下一步；`ready-for-human` 表示它已准备好由人类来 merge。

每一个经过 triage 的 issue 都应恰好携带一个 category 角色和一个 state 角色。如果 state 角色相互冲突，先标记出来并询问 maintainer，然后再做任何其他事。

这些是规范的角色名称——issue tracker 中实际使用的 label 字符串可能不同。这份映射应该已经提供给你了——如果没有，运行 `/setup-matt-pocock-skills`。

状态流转：一个未打标签的 issue 通常先进入 `needs-triage`；从那里它移动到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者回复，`needs-info` 就回到 `needs-triage`。maintainer 可以随时覆盖——对看起来不寻常的流转加以标记，并在继续之前先询问。

## 调用

maintainer 调用 `/triage` 并用自然语言描述他们想要什么。解读这个请求并付诸行动。示例：

- "Show me anything that needs my attention"
- "Let's look at #42"（issue 或 PR）
- "Move #42 to ready-for-agent"
- "What's ready for agents to pick up?"

## 展示需要关注的内容

查询 issue tracker，并呈现三个桶，最旧的在前：

1. **Unlabeled** — 从未经过 triage。
2. **`needs-triage`** — 评估进行中。
3. **`needs-info` with reporter activity since the last triage notes** — 需要重新评估。

当 PR 在范围之内时，把外部 PR 也纳入这些桶，并为每一行标注 `[PR]` 或 `[issue]`。发现环节只浮现*外部* PR（tracker 配置定义了谁算外部）——某个协作者正在进行中的 PR 不是 triage 工作。这个过滤仅用于发现环节；一个被明确点名的 PR 无论作者是谁都会被 triage。

显示数量，并为每一项给出一行摘要。让 maintainer 来挑选。

## triage 一个具体的 issue 或 PR

1. **Gather context.** 读取完整的 issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还有 diff）。解析任何先前的 triage 笔记，这样你就不会重新追问已解决的问题。使用项目的领域词汇表探索代码库，尊重该区域中的 ADR。对照代码库运行两项检查：(a) **冗余**——按领域概念（而不仅仅是请求的措辞）搜索所请求行为的现有实现，并报告你找过哪些地方。如果找到了，它就是一个已实现的 `wontfix`（第 5 步）。(b) **先前被拒**——阅读 `.out-of-scope/*.md`，并浮现任何与这个请求相似的条目。

2. **Recommend.** 告诉 maintainer 你的 category 和 state 推荐及其理由，外加一份与该请求相关的简短代码库摘要——包括它是否已经实现。等待指示。

3. **Verify the claim.** 在任何 grilling 之前，先检查这个说法是否站得住脚。对于 bug，按照报告者的步骤复现它。对于 PR，确认这个 diff 做到了它所声称的事——把它 checkout 出来，运行相关的 test 或命令。报告发生了什么：已确认（附上代码路径）、失败，或细节不足（一个强烈的 `needs-info` 信号）。一次得到确认的核验会让 agent brief 有力得多。

4. **Grill (if needed).** 如果这个请求需要进一步充实，就把 `/grilling` 和 `/domain-modeling` skill 一起运行——一次一个问题地把它 grill 成形，随着决策落定，就地打磨领域术语并更新 `CONTEXT.md`/ADR。

5. **Apply the outcome:**
   - `ready-for-agent` — 发布一条 agent brief 评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 与 agent brief 相同的结构，但注明为什么它不能被委托（判断性决策、外部访问、设计决策、手工测试）。
   - `needs-info` — 发布 triage 笔记（模板见下）。
   - `wontfix` — 关闭，评论视*原因*而定：
     - **Already implemented** — 这个变更已经存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（那个知识库是为*被拒绝*的请求准备的，而不是为已构建的东西）。
     - **Rejected (bug)** — 礼貌地解释，然后关闭。
     - **Rejected (enhancement)** — 写入 `.out-of-scope/`，从一条评论链接到它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 应用该角色。如果有部分进展，可选择附一条评论。

## 快速 state 覆盖

如果 maintainer 说 "move #42 to ready-for-agent"，就信任他们并直接应用该角色。确认你将要做什么（角色变更、评论、关闭），然后行动。跳过 grilling。如果在没有 grilling 会话的情况下移到 `ready-for-agent`，询问他们是否想写一份 agent brief。

## needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把 grilling 期间解决的一切捕获到 "established so far" 之下，这样这些工作就不会丢失。问题必须具体且可付诸行动，而不是 "please provide more info"。

## 恢复上一场 session

如果该 issue 或 PR 上已存在先前的 triage 笔记，就阅读它们，检查报告者是否已回答了任何悬而未决的问题，并在继续之前呈现一幅更新后的图景。不要重新追问已解决的问题。
